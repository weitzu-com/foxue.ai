# foxue.ai 不可变保存发行协议

本协议定义如何把一个已经完成审计的 GBCR 版本变成公开、不可修改、可离线恢复的长期保存基线。它解决的是“未来维护者如何证明拿到的代码和语料没有被替换”，不把任何单一供应商的寿命误写成 100 年保证。

## 1. 第一性原理

长期保存至少需要同时满足五个条件：

1. **身份唯一**：发行标签、Git 标签对象、提交和文件摘要必须一一绑定；
2. **内容完整**：源码、治理文档、受控语料、可达 Git 历史和恢复手册必须进入同一恢复包；
3. **发布原子性**：所有资产上传并核对完成之前，发行只能是可修改的草稿；
4. **故障可替换**：GitHub、Software Heritage、对象存储、离线介质和域名不是彼此的单点替代品；
5. **结论可证伪**：覆盖率、权利、质量和保存状态只报告已经由清单、哈希和外部检查证明的部分。

因此，“网站在线”“经藏对象已就绪”“恢复包存在”“全球佛经覆盖达到 99%”是四个不同命题。任何一个命题都不能代替另一个。

## 2. 自动化入口

工作流位于 `.github/workflows/preservation-release.yml`。它在以下两种情况下运行：

- 推送形如 `gbcr-vMAJOR.MINOR.PATCH` 的标签；
- 维护者手动输入一个已经存在的同格式标签。

修改工作流、验证器或本协议的普通 PR 只运行 `scripts/validate-preservation-release-workflow.mjs`，并保持仓库内容只读。正式标签或手动发行事件通过验证后，只有 `release` 任务临时获得 `contents: write`。

只有注释标签（annotated tag）可以成为发行标签。轻量标签会被拒绝，因为注释标签提供独立标签对象，可与目标提交和 GitHub 发行证明共同校验。

建议的发行命令：

```bash
git switch main
git pull --ff-only
pnpm verify
git tag -a gbcr-vX.Y.Z -m "foxue.ai GBCR vX.Y.Z preservation baseline"
git push origin gbcr-vX.Y.Z
```

不要移动或复用发行标签。不可变发行发布后，相关标签和发行资产应被视为永久标识。

## 3. 发布门

自动化在创建公开发行前按顺序执行以下门禁：

| 门 | 失败条件 | 保护目标 |
|---|---|---|
| 标签格式 | 不符合 `gbcr-vX.Y.Z` | 防止临时标签误发 |
| 标签类型 | 不是注释标签 | 保留独立标签对象 |
| 提交一致性 | checkout 与标签目标不同 | 防止打包错误提交 |
| 主线可达 | 标签目标不在 `origin/main` 历史中 | 防止未合并代码获得正式身份 |
| 锁定安装 | lockfile 无法复现 | 防止依赖漂移 |
| 全量验证 | `pnpm verify` 失败 | 阻止站点、语料或边缘包错误进入发行 |
| 保存构建 | `pnpm preserve` 失败 | 阻止不完整恢复包 |
| SHA-256 | 任一资产本地复核失败 | 阻止损坏资产上传 |
| 草稿资产 | 数量、名称、大小或状态不一致 | 阻止半完成发行公开 |
| 不可变状态 | 发布后没有进入 immutable | 阻止可被替换的“正式基线” |
| 发行证明 | `gh release verify` 失败 | 阻止无法验证来源的发行 |
| 单资产证明 | 任一 `verify-asset` 失败 | 阻止资产与发行证明脱钩 |

工作流固定所有第三方 GitHub Actions 到完整提交 SHA，使用 Node.js 22 和锁定的 pnpm 版本。发行任务只授予 `contents: write`，不授予仓库管理、Issues 或其他权限。

## 4. 资产格式

每个发行包含四项资产：

- `foxue-ai-preservation-<tag>-<commit>.tar.zst`：外层压缩恢复包；
- `preservation-manifest.json`：提交、源时间、关键资产和内部文件摘要；
- `SHA256SUMS`：恢复包内部文件校验和；
- `RELEASE-SHA256SUMS`：公开发行三项内容资产的外部校验和。

外层 tar 使用排序路径、Git 提交时间、数值化的固定属主和属组生成，再以 zstd 压缩。这里的确定性目标是消除常见的文件顺序与时间戳漂移；最终可信身份仍以发行中的 SHA-256 和 GitHub 发行证明为准。

`RELEASE-NOTES.md` 只用于创建发行说明，不作为第五项发行资产，避免说明文本与发行元数据形成两个权威来源。

## 5. 原子发布和失败恢复

GitHub 的不可变保护在公开发布之后生效。因此工作流严格使用以下状态机：

```text
校验标签 → 验证全站 → 构建保存包 → 本地校验
    → 创建草稿 → 上传四项资产 → 远端核对
    → 发布草稿 → 核对 immutable → 验证发行证明和每项资产
```

如果流程在公开之前中断，重新运行同一标签会恢复已有草稿，并重新上传同名资产。若同名发行已经公开，流程拒绝修改并立即失败。这个规则保证重试不会绕过不可变边界。

若公开动作成功但证明短暂尚未可见，流程最多轮询 60 秒。超过时间仍不能验证时任务失败，维护者必须把它作为供应链事件调查；不能仅因页面可下载就宣布发行完成。

## 6. 下载和恢复验证

从公开发行恢复时，先验证发行证明，再验证文件，最后解包：

```bash
gh release download gbcr-vX.Y.Z --repo weitzu-com/foxue.ai
gh release verify gbcr-vX.Y.Z --repo weitzu-com/foxue.ai
sha256sum -c RELEASE-SHA256SUMS
zstd -t foxue-ai-preservation-gbcr-vX.Y.Z-<commit>.tar.zst
zstd -dc foxue-ai-preservation-gbcr-vX.Y.Z-<commit>.tar.zst | tar -xf -
cd <commit>
sha256sum -c SHA256SUMS
git bundle verify foxue.ai-<commit>-history.bundle
```

macOS 可将 `sha256sum` 替换为 `shasum -a 256`，或安装 GNU coreutils。恢复后的完整建站步骤继续遵循 `docs/RECOVERY.md`。

### 6.1 自动恢复演练

`.github/workflows/preservation-recovery-drill.yml` 每季度从公开网络选择语义版本最高的不可变 GBCR 发行，并在全新临时目录中完成一次真实恢复。普通 PR 只运行恶意夹具与合法夹具测试，不下载生产发行；定时和手动任务保持 `contents: read`，不能修改发行。

演练不是只检查页面是否返回 200，而是依次证明：

1. GitHub 发行和四项资产的证明均可验证；
2. `RELEASE-SHA256SUMS` 与全部下载内容一致；
3. zstd 流完整，外层 tar 没有绝对路径、路径穿越、重复成员、符号链接、硬链接或特殊文件；
4. 包内外清单与 `SHA256SUMS` 逐字节一致；
5. 源码 tar 同样通过安全成员检查并实际解压；
6. `criticalAssets` 中每个文件都在恢复目录重新计算 SHA-256；
7. Git bundle 能在新的裸仓库中通过 `bundle verify`、恢复记录提交并通过严格 `fsck`；
8. 最终生成 `RECOVERY-DRILL-REPORT.json`，失败时整个任务失败，不允许“带错通过”。

手动复核任一不可变版本时可在 Actions 中输入精确的 `gbcr-vX.Y.Z` 标签。空输入只选择已经公开且 `isImmutable=true` 的最高语义版本，不会把草稿或可变发行当作恢复基线。

Actions 报告保留 90 天，只是运行证据而不是长期副本。机构镜像和离线 WORM 保管人应定期导出报告，并与相应发行 SHA-256 一起进入长期审计日志。

## 7. 与 Software Heritage、R2 和离线介质的关系

各副本保存的故障域不同：

| 副本 | 擅长保存 | 不能替代 |
|---|---|---|
| GitHub 不可变 Release | 标签、提交、二进制资产、发行证明 | 独立机构存档与离线介质 |
| Software Heritage | Git 对象、分支与标签的公共历史 | Release 大型二进制、在线语料对象 |
| Cloudflare R2 | 内容寻址语料对象的全球只读分发 | Git 历史、治理记录、离线灾备 |
| 离线 WORM/冷存储 | 跨账户、跨云恢复 | 日常访问和自动健康检查 |
| 机构镜像 | 法人交接、长期托管和独立审计 | 社区实时协作 |

R2 尚未启用时，`canon.foxue.ai/ready` 必须保持非就绪状态；GitHub 发行成功也不能把 R2 状态改写为就绪。反过来，R2 在线也不能证明 Git 历史和治理文件可恢复。

## 8. 3-2-1-1-0 保存策略

“3-2-1”只是起点。foxue.ai 的正式目标是 3-2-1-1-0：

- 至少 3 份副本；
- 至少 2 种介质；
- 至少 1 份异地；
- 至少 1 份离线或不可变；
- 每次演练必须达到 0 个未解释的校验错误。

每个 GBCR 正式版本至少应完成：

1. GitHub 不可变发行；
2. Software Heritage 新快照可发现；
3. 一份与云账户隔离的离线 WORM 或冷存储副本；
4. 一份由不同组织控制的机构镜像；
5. 从零恢复演练，并记录用时、失败点和全部哈希结果。

最低演练节奏为每季度自动恢复最新不可变发行；每年另行人工抽检一个较早版本，并从与 GitHub 账户、Cloudflare 账户都隔离的介质恢复。只运行 CI 不能满足异地和离线副本要求。

在第 3、4 项没有实际托管方和介质证据之前，只能写“长期保存链已建立”，不能写“保证运行 100 年”。

## 9. 权限和密钥纪律

- 发行工作流只使用短期 `GITHUB_TOKEN`；
- 不把 Cloudflare、域名、数据库或第三方 API 密钥放入恢复包；
- 生产密钥必须由密码管理器和离线继任封套分别托管；
- 人员离开、设备丢失、令牌疑似泄露或权限异常时立即轮换；
- 每年至少验证两名独立继任维护者能完成下载、校验、构建和发布演练。

任何在终端、浏览器录屏、CI 日志或聊天记录中出现过的长期凭据都应视为已泄露并轮换。

## 10. 发布完成定义

只有同时满足以下条件，某个 GBCR 版本才可以标记为“不可变保存发行完成”：

- 标签为注释标签且目标提交位于主线；
- 全量质量验证通过；
- 四项资产全部上传并匹配本地大小和摘要；
- 发行已公开且 `isImmutable=true`；
- 发行证明和四项单资产证明全部通过；
- 下载路径、清单和恢复命令已经由独立环境复核；
- 监控不会把 Actions 30 天工件当作长期副本。

这一定义故意比“Release 页面存在”更严格。百年工程的核心不是承诺永远不坏，而是让每一次损坏都能被发现、定位、替换和复核。
